# Security and privacy

## Secrets: used in approved ways, never shown to agents

Passport numbers, portal logins and test registration numbers live in a vault; notes hold `secret:name` references only. The honest threat model: whoever receives a value has it. So Brainiac controls _where_ a value can go.

| Way to use a secret                       | Where the value goes                                                             | Guarantee                                                         |
| ----------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **`fill_form`** via the browser extension | Only into a form field on the domain saved with the secret, after a user gesture | The agent never receives the value; lookalike domains are refused |
| **Show to you**                           | Your screen, after a passkey check                                               | Never available to agents                                         |

- **No secret injection into commands**: a command that receives a secret can store or print it (even `gh auth login --with-token` lets `gh auth token` print it back), and on a laptop an agent's shell is your shell. So there's no `brainiac with`. You copy a value yourself after the passkey "show" when you need it in a terminal.
- **Vault documents** (passport, ID, visa, bank statement scans) never reach agents as text, page images or file URLs; `get` returns a redacted summary (see "The contract"). The rules live in `packages/base/src/vault.ts`; `viewFile` is the one projection of a file for every read surface. Traps it guards: the checks (`packages/core/src/checks.ts`) err toward finding, since a false hit only keeps a file in the vault. They read only plain text, markdown or CSV whose bytes hide nothing (no markup, character references or long encoded runs); anything else is `unreadable` and can't be cleared. A PDF gets its text layer and metadata from a `file` job (`installFile`), and the checks run over all of it. That is all of the PDF's text only when nothing else on it can print any, so `pdfHidesText` holds back a PDF with an image (an XObject or inline), an attached file, form fields, any annotation but a link, a Type3 font, encryption, an earlier revision kept by an incremental save, or a stream it can't open; it trusts no dictionary to say what a stream holds, inflating each one (within a size limit) and judging what comes out. It guards against what ordinary writers put in a PDF (a scan, a photo, a filled form): a file crafted to slip past it can only hide what its maker already knew. Such a PDF, or one with a page of garbled text or a table with no numbers (`needsReading`), stays unclassified, and so does every image file, since `toMarkdown` describes images rather than transcribing them. Reading those is #103. The checks only tighten: what one extraction found stays found, and a passport parsed after upload is written as its uploader (a connection's waits as a proposal). A file's id is an HMAC under the data key, not a plain hash, so an agent can't test guesses at a vault file's contents against it offline (uploading the exact bytes still shows whether the record has them). A connection's kind is only a suggestion; the person confirms. Loosening a confirmed kind needs a passkey over `kindHash`, which names the file's `rev`. A passport's MRZ is parsed only when every check digit holds; its number goes to a secret named for the file, so no upload can overwrite one.
- **Policies**: per secret, `ask` (default: an approval each time, showing the domain) or `allow` for the saved domain, or `never`.
- **Storage**: one cloud vault for every mode; secrets are never written to a laptop. Each secret, and every uploaded file, is sealed (AES-256-GCM, bound to its name or hash) with the record's data key, which the record keeps in `meta` wrapped by the stage's `VAULT_KEY` in Cloudflare's Secrets Store. A secret is decrypted only in the fill path. Replacing `VAULT_KEY` makes every record's vault unreadable, so prod's is protected like any prod resource; rotating it is not built yet. Every use is audited.

## Security and privacy

- **Isolation**: one DO per record; the base id comes from the session or the token (tokens embed it), never from a URL; R2 keys are built server-side; CI runs a cross-tenant attack suite against every route and tool.
- **Authorization projection** on every read surface, including indexes, caches and file URLs (see "RAG"), with canary tests.
- **Approvals** are WebAuthn passkey signatures over the plan hash, verified in the DO (see "The contract"). Two passkeys are requested at sign-up; losing both means a 72-hour recovery wait with notices. Every change (a mutation, a sync edit, an undo) is judged at the end of its own transaction on each note it wrote, as the note started and ended, so clearing `verified` is itself held and clear-then-edit fails at its first step. A held change is rolled back whole and returns its plan (each note's id, base revision, path, class and effect); the signature covers all of it. An approval is used once, and only by a change with that exact effect. Adding, removing or redirecting a `supersedes` edge into a verified note is held too, and deleting more than five notes is held whatever they hold: in one change, or across a connection's changes in a day (counted from the change feed), so one delete per call doesn't get around it. A change to more than 20 notes (a bulk `update`) needs a signature too, which a review session that showed them all covers. A review session belongs to whoever started it (only they can open it), and covers edits to the notes it showed (a `supersedes` edge it moves must point at a note it showed too) (for an undo, deletes and restores too, never a bulk delete). Front-matter is judged on its JSON copy, so it is read as YAML 1.2 core whatever its `%YAML` line says, and anything JSON would lose or blur is refused: tags, `.inf`, `.nan`, integers past 2^53, keys that aren't plain names (a mapping, a list, null or an alias), keys that read alike (`1` and `"1"`) and `__proto__` keys. A `verified` block whose `fields` isn't a list of names covers every field. Approvals judge values, not their spelling: rewriting a verified value's text without changing it (`100` as `0100`, a comment beside it) needs no signature. Only the site's session route may call `approve`, `startReview` and `openReview`. Known gap: `supersedes` is judged when a note sets it, not when its target is verified later.
- **Connections** (`packages/base/src/connections.ts`, `hold.ts`, `proposals.ts`): a tool call names its connection, and the record loads its level, sensitive scope and hold from its own table, never from the caller; its actor is always `connection:<id>`. Connecting gives the floor: propose, no sensitive scope, a 3-day hold. Raising the level, granting the sensitive scope or shortening the hold needs a passkey signature over `grantHash` of the exact grants and the connection's `rev`, which every grant change bumps, so an old signature can't raise a connection lowered since; tightening needs none. Without the sensitive scope a connection gets "no note" for a sensitive note on every path: not its revision, not its values in a failed check, a path clash doesn't name it, and an undo that touched one is refused. A read connection changes nothing and a propose one's every change waits for the person. A write one's change is held when its effect, judged like approvals on each note as the transaction found and left it, changes or removes an existing value of a held type (`held: true` in the manifest), rewrites existing body text in one (a new paragraph or heading after it is new; text run onto its last line, or on the next line without a blank one, changes what that paragraph says), deletes one or brings one back from a tombstone with other values, moves a note out of a held type's folder or moves a held-type note anywhere (moves arrive with #38), or points `supersedes` at a held-type note. The approval list is judged first, and a signature that satisfies it also releases the change from the hold. A held change is rolled back and kept with the mutation that applies it (a held undo also keeps the last `seq` it covered, so edits added to the run later aren't undone with it); when its hold runs out the alarm applies it with the connection's current grants, and one whose connection is gone or below write waits for the person. A release applies exactly the effect that was held or nothing: onto a note changed since, a field patch still applies if replaying it does the same, and anything else becomes a conflict (or, for an undo, waits for the person). A longer hold pushes back what is already waiting, and lowering a connection below write leaves its waiting changes to the person. Only the site's session route decides proposals: accepting one applies it as the person's change, so their review session covers it, and accepting a conflict writes its kept-out side; a connection may withdraw only its own. Sync edits carry no connection: they're unattributed (contract §3), so they skip the hold, never the approval list; a read-level connection's sync edits are refused. A CLI token is `brn_<base id>_<secret>`: `/sync`, `/cli/logout` and `/mcp` route it by the id, and the record keeps only a hash of the whole token, so the same secret under another id matches nothing. A session reaches its record through the base registry (Neon `bases`), and the Worker drops any actor header a client sends before setting the one the record trusts. An MCP client that connects again gets its existing connection back, grants and all, so the account page's Disconnect ends the record's connection first (`disconnectApp`), then the consent and tokens in Neon: if Neon then fails, the app comes back at the floor, never with its grants. A connection without the sensitive scope can't add, redirect or remove a `supersedes` edge to a note it can't see, or to none: either is refused alike, so the answer never says what a hidden note is. Known gap: removing a `supersedes` edge into a held-type note, or deleting the note that holds it, isn't held when that note's own type isn't held.
- **Audit** (`packages/base/src/audit.ts`): every tool call writes one `audit` row in the call's own transaction (`callTool`), so a change and its row land together or neither does, a refused call included. The row names the connection, the tool, every note the answer showed or the call changed (never one hidden from it), and the approval it cited if the record issued one. No tool reads the log; the person sees each connection's last 50 calls on the account page. Sync edits and the person's own changes aren't tool calls and aren't in it; the change feed already says who made them. Known gap: rows are kept forever, and a disconnected connection's rows stay but aren't shown.
- **Prompt injection**: the main risk is your own Claude reading a hostile PDF or email and then acting. Inside Brainiac, everything that can destroy or leak through Brainiac (secret use, form submits, email, privacy loosening, permission changes, bulk deletes, verified values) is on the approval list, which no agent can satisfy. Text from files, emails and pages is also marked `untrusted` in tool results, as a hint.
- **What Brainiac can't stop**: anything a connection can read, your Claude can send elsewhere through its other connectors (email, web). So the sensitive scope is off by default for every connection; you grant it per connection when you connect your own Claude, and the default is checked by a canary eval.
- **Filer access**: automatic background filing (no person present) handles normal material only. Sensitive items wait for your own Claude session whose connection you granted the sensitive scope; that connection keeps exactly the access you granted, and the inbox lease only makes it the one agent filing that item. Unclassified items stay redacted for everyone until your confirmation tap clears them. A lease is per `inbox` call's lease id, not per connection, because the daemon's headless run and your own Claude Code session share the device's token; `update` and `undo` leave a leased item alone, and `done` deletes only the revision the lease handed out. With `brainiac filing on` (which saves where `claude` is, since the login service has only the system PATH), the daemon starts a headless run for new normal inbox items, one run at a time, in an empty working directory with `--restricted --tools ""` (no built-in tools, user and project settings ignored), `--strict-mcp-config` with a config containing only Brainiac, and `--allowedTools "mcp__brainiac__*"`, so the run can't reach a shell, files or your other connectors. Its Brainiac server is `brainiac mcp serve --background`, which sends `brainiac-background: 1`, and the record narrows the connection for those calls (`inBackground`): propose and no sensitive scope, whatever you granted the device, so every change waits for you and no hold releases it; it also can't add inbox items, so a run can't start the next one, or withdraw proposals, which on a shared connection include your own sessions'. The header is trusted from any client because it only narrows. The `filing` eval (`evals/filing`) starts a real headless run through the daemon's own `fileInbox`, asserts its tool inventory is Brainiac's tools and nothing else, and files an injection corpus that never gets a change applied. Changes to numbers, dates or verified facts come as proposals with the source page.
- **Laptop copies**: on disk, the sensitive scope binds only Brainiac's tools, not programs that read files. That's why sensitive notes stay in the cloud by default, vault-document files are never written to disk, and the hook blocks Read, Grep and Glob on sensitive folders, `documents/files/` and `inbox/`. The daemon uploads inbox files right away and keeps them out of the local index.
- **Email-in**: accepted only from your verified addresses; anything else is quarantined for you to release. Attachments go through the same ingest checks as uploads.
- **Uploads**: type sniffed from bytes, size caps per plan, decompression limits, executables rejected, Office macros flagged, HTML and SVG served only from the sandboxed origin. Built so far: the site's upload (`apps/worker/src/site.ts`, 25 MB cap, the uploader's type kept as given) and the sandboxed origin; sniffing, per-plan caps and the rest are not.
- **The usercontent origin** (`apps/worker/src/usercontent.ts`): every file's bytes come only from `usercontent.<domain>` (`USERCONTENT_ORIGIN`; a stage without a custom domain has none and shows no files), at `/f/<token>`, and every answer there, 404s included, carries `Content-Security-Policy: sandbox; default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'`, `nosniff` and `private, no-store`. It reads no cookie and sets none, and answers nothing but files, so a page there can't act as the person even though browsers send it the site's cookies (`/sync` and every site route also refuse another origin's pages). The site's origin answers `/f/` with a 404. The token (`brf_<base id>_<secret>`) is minted by the record for the person only, never a connection, opens one file once and lasts a minute; the record keeps its hash and the site origin that asked, which is the only origin CORS lets read the bytes. Unclassified and vault originals need the session's passkey proof (`vouchedUntil`, 10 minutes, the same proof the account page asks for): the site runs Better Auth's passkey sign-in to get it. The site shows HTML and SVG in an `<iframe sandbox>` with no flags, images with `<img>`, and fetches a PDF's bytes once for pdf.js.
- **Auth**: Better Auth 1.7, self-hosted in the Worker with its tables in Neon: passkeys (sign-in and approvals share the same credentials), email codes, Google and GitHub, JWT, and `@better-auth/mcp` + `@better-auth/cimd` as the OAuth 2.1 server for MCP (2026-07-28 profile). $0 at any scale, but we own OAuth security. MCP clients identify by a metadata URL (CIMD), and there's no open registration endpoint. CIMD needs an app-supplied fetch transport and ships only a Node one, so the Worker has its own (`apps/worker/src/auth/cimd-fetch.ts`). It can't build a `Request` from the plugin's options, because workerd refuses their `redirect: "error"`. It skips the Node transport's DNS pinning: the plugin already refuses client_ids on private or reserved hosts, on the edge a Worker's fetch reaches no private network, and `global_fetch_strictly_public` routes a fetch to one of our own zones through Cloudflare's front door rather than straight to its origin. It enforces HTTPS, GET or HEAD, and no redirects. `/mcp` checks tokens against the signing keys in-process (Better Auth's `requireMcpAuth` fetches our own `/jwks` over HTTP, which timed out behind a public hostname), answers 503 rather than "invalid token" when it can't load the keys, and takes a DPoP-bound token only with a fresh proof from its key (each proof used once, remembered in Neon's verification table, so a replay is caught on any isolate). Access tokens are JWTs nothing can recall; they live an hour, because Codex doesn't refresh and sends the person through sign-in again each time one runs out. Revocation acts on refresh: a refresh token is rotated on every use, with a 30-second window for a client to retry a refresh whose reply it lost, and a rotated one used after that ends the whole grant. The account page lists connected apps, and Disconnect deletes the consent and then the client's tokens; Better Auth's own `/oauth2/delete-consent` and `/oauth2/update-consent` are switched off because they leave the tokens working. The token endpoint checks for consent after it issues tokens, so a refresh that raced a disconnect fails instead of keeping a grant nobody agreed to; it refuses a grant that names no resource, whose opaque token it couldn't check. A disconnected app keeps its current access token for up to an hour, so `/mcp` also finds the consent behind it on every request and answers 401 without one; dev tokens (`brainiac-dev`) have none and are taken only where dev sign-in exists. `/mcp` also takes a CLI token, routed by the id inside it and checked by that record's `authenticate`, which is how `brainiac mcp serve` reaches the record. A tool's failure reaches the agent as a fixed message; the error itself goes only to the logs. The issuer, sign-in and consent pages share `/mcp`'s origin: moving MCP to its own hostname would break passkey sign-in there (passkeys are bound to the site's host) and the session cookie, so `authorization_servers` would have to name the site's origin instead. Conformance runs: Claude Code, MCP Inspector, Codex and claude.ai's published client each sign in by CIMD and reach `/mcp`; Claude Code and claude.ai's client refresh, and after Disconnect none of them gets back in without consenting again. Turnstile on sign-up (sending an email code and starting Google or GitHub sign-in, the two ways an account gets made). A new passkey can approve at once only if it's the account's first, the account is under an hour old and its address is verified (sign-up; an OAuth account can arrive with someone else's unverified address), or the session adding it proved a passkey that can approve in the last 10 minutes (the sign-up passkey counts, so the second one the page asks for doesn't wait). Otherwise it waits 72 hours, and the notice to the verified address goes out before the passkey gets its date; if the address isn't verified or the send fails, the passkey is removed. A session cookie alone never vouches, so a stolen one can't skip the wait. A waiting passkey can sign in but can't vouch for another. Removing a passkey that approves needs the same 10-minute proof, so someone holding only the email can't delete the real passkeys and wait the owner out; a passkey that can't approve yet is removed without proof, each removal a single conditional delete. Removing your own last approving passkey is allowed after a warning: as with losing it, the next one goes through recovery (after the sign-up hour). Better Auth's rate limit is switched on explicitly (it keys off `NODE_ENV`, which Workers don't set), and the email-code password reset is off since nobody has a password. Session checks use a 5-minute cookie cache, so a short Neon outage signs nobody out. Every stage except prod also has dev sign-in (`apps/worker/src/dev.ts`): whoever holds `DEV_SIGN_IN_TOKEN` from Doppler `dev` becomes the fictional fixture student, or a tagged copy of it, without a code or passkey, and can mint a `/mcp` token for it. It never reaches prod three ways: `alchemy.run.ts` doesn't bind the token there, the Worker answers 404 for `/dev/` when `STAGE` is `prod`, and the deploy doctor reads the prod Worker's bindings and fails if the token is one. The token travels in the link's fragment and then a header, never a request URL, so request logs don't keep it (the browser's own history may); a wrong token looks the same as no route, and the comparison is over hashes in constant time. A dev session can add a passkey like any session, and on a fresh tagged account the first one approves at once; that reaches only fictional fixture accounts on non-prod stages. Managed fallbacks: Neon Managed Better Auth, then WorkOS AuthKit (see "Decisions").
- **Residency, stated narrowly**: EU accounts get EU-jurisdiction DOs and EU R2, and a Neon project in an EU region. Your own Claude processes what its tools return, under your Anthropic account's terms. Workers AI and treg providers may process data outside the EU. The settings page lists every processor and its region; anything not verified isn't claimed.
- **Backups, stated honestly**: DO point-in-time recovery (30 days) and R2 durability protect against bugs and mistakes, not against a Cloudflare-wide outage. A local copy, and the always-available export, are the real off-provider copies. Recovery targets: a single record restored within 4 hours, losing at most 1 hour of changes. A quarterly drill restores a fixture record (notes, files, schema, secret keys) into a staging stack and runs the parity tests on it.
