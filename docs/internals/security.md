# Security and privacy

## Secrets: used in approved ways, never shown to agents

Passport numbers, portal logins and test registration numbers live in a vault; notes hold `secret:name` references only. The honest threat model: whoever receives a value has it. So Brainiac controls _where_ a value can go.

| Way to use a secret                       | Where the value goes                                                             | Guarantee                                                         |
| ----------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **`fill_form`** via the browser extension | Only into a form field on the domain saved with the secret, after a user gesture | The agent never receives the value; lookalike domains are refused |
| **Show to you**                           | Your screen, after a passkey check                                               | Never available to agents                                         |

- **No secret injection into commands**: a command that receives a secret can store or print it (even `gh auth login --with-token` lets `gh auth token` print it back), and on a laptop an agent's shell is your shell. So there's no `brainiac with`. You copy a value yourself after the passkey "show" when you need it in a terminal.
- **Vault documents** (passport, ID, visa, bank statement scans) never reach agents as text, page images or file URLs; `get` returns a redacted summary (see "The contract").
- **Policies**: per secret, `ask` (default: an approval each time, showing the domain) or `allow` for the saved domain, or `never`.
- **Storage**: one cloud vault for every mode; secrets are never written to a laptop. Each secret is encrypted with the record's data key, wrapped by a key in Cloudflare's Secrets Store, and decrypted only in the fill path. Every use is audited.

## Security and privacy

- **Isolation**: one DO per record; the base id comes from the session or the token (tokens embed it), never from a URL; R2 keys are built server-side; CI runs a cross-tenant attack suite against every route and tool.
- **Authorization projection** on every read surface, including indexes, caches and file URLs (see "RAG"), with canary tests.
- **Approvals** are WebAuthn passkey signatures over the plan hash, verified in the DO (see "The contract"). Two passkeys are requested at sign-up; losing both means a 72-hour recovery wait with notices. Every change (a mutation, a sync edit, an undo) runs as one transaction, nested as a savepoint when the sync handler holds one, and is judged at its end on each note it wrote, as the note started and ended (`packages/base/src/approvals.ts`). A change needing an approval it lacks is rolled back whole and comes back as `needsApproval` with its plan: each note's id, base revision, path and effect, hashed as sorted-key JSON into the base64url challenge. Because the judge reads the stored note, not the request, clearing `verified` is itself held, so clear-then-edit fails at its first step. The DO checks the assertion (origin, RP ID, user verification, a counter past the last one it saw, a passkey whose `approvesAt` has passed) against the owner's passkey, which the Worker loads from Neon; the approval is then used up in the transaction it lets through, and a plan is approved once. Only the site's session route may call `approve` and `openReview`; no MCP tool or token reaches them. A review session covers edits to the notes it showed, and for an undo, deletes and restores too; creates, deletes, moves and anything off the note list need their own signature.
- **Prompt injection**: the main risk is your own Claude reading a hostile PDF or email and then acting. Inside Brainiac, everything that can destroy or leak through Brainiac (secret use, form submits, email, privacy loosening, permission changes, bulk deletes, verified values) is on the approval list, which no agent can satisfy. Text from files, emails and pages is also marked `untrusted` in tool results, as a hint.
- **What Brainiac can't stop**: anything a connection can read, your Claude can send elsewhere through its other connectors (email, web). So the sensitive scope is off by default for every connection; you grant it per connection when you connect your own Claude, and the default is checked by a canary eval.
- **Filer access**: automatic background filing (no person present) handles normal material only. Sensitive items wait for your own Claude session whose connection you granted the sensitive scope; that connection keeps exactly the access you granted, and the inbox lease only makes it the one agent filing that item. Unclassified items stay redacted for everyone until your confirmation tap clears them. The daemon's headless connection is propose-level. It starts headless runs in an empty working directory with `--restricted --tools ""` (no built-in tools, user and project settings ignored), `--strict-mcp-config` with a config containing only Brainiac, and `--allowedTools "mcp__brainiac__*"`, so the run can't reach a shell, files or your other connectors. A `filing` eval case starts a real headless run and asserts its actual tool inventory is Brainiac's tools and nothing else. Changes to numbers, dates or verified facts come as proposals with the source page.
- **Laptop copies**: on disk, the sensitive scope binds only Brainiac's tools, not programs that read files. That's why sensitive notes stay in the cloud by default, vault-document files are never written to disk, and the hook blocks Read, Grep and Glob on sensitive folders, `documents/files/` and `inbox/`. The daemon uploads inbox files right away and keeps them out of the local index.
- **Email-in**: accepted only from your verified addresses; anything else is quarantined for you to release. Attachments go through the same ingest checks as uploads.
- **Uploads**: type sniffed from bytes, size caps per plan, decompression limits, executables rejected, Office macros flagged, HTML and SVG served only from the sandboxed origin.
- **Auth**: Better Auth 1.7, self-hosted in the Worker with its tables in Neon: passkeys (sign-in and approvals share the same credentials), email codes, Google and GitHub, JWT, and `@better-auth/mcp` + `@better-auth/cimd` as the OAuth 2.1 server for MCP (2026-07-28 profile). $0 at any scale, but we own OAuth security. MCP clients identify by a metadata URL (CIMD), and there's no open registration endpoint. CIMD needs an app-supplied fetch transport and ships only a Node one, so the Worker has its own (`apps/worker/src/auth/cimd-fetch.ts`). It can't build a `Request` from the plugin's options, because workerd refuses their `redirect: "error"`. It skips the Node transport's DNS pinning: the plugin already refuses client_ids on private or reserved hosts, on the edge a Worker's fetch reaches no private network, and `global_fetch_strictly_public` routes a fetch to one of our own zones through Cloudflare's front door rather than straight to its origin. It enforces HTTPS, GET or HEAD, and no redirects. `/mcp` checks tokens against the signing keys in-process (Better Auth's `requireMcpAuth` fetches our own `/jwks` over HTTP, which timed out behind a public hostname), answers 503 rather than "invalid token" when it can't load the keys, and takes a DPoP-bound token only with a fresh proof from its key (each proof used once, remembered in Neon's verification table, so a replay is caught on any isolate). Access tokens are JWTs nothing can recall; they live an hour, because Codex doesn't refresh and sends the person through sign-in again each time one runs out. Revocation acts on refresh: a refresh token is rotated on every use, with a 30-second window for a client to retry a refresh whose reply it lost, and a rotated one used after that ends the whole grant. The account page lists connected apps, and Disconnect deletes the consent and then the client's tokens; Better Auth's own `/oauth2/delete-consent` and `/oauth2/update-consent` are switched off because they leave the tokens working. The token endpoint checks for consent after it issues tokens, so a refresh that raced a disconnect fails instead of keeping a grant nobody agreed to; it refuses a grant that names no resource, whose opaque token it couldn't check. A disconnected app keeps its current access token for up to an hour, so every tool call must also find the consent behind its connection (#13, #17); `/mcp` serves no tools until then. The issuer, sign-in and consent pages share `/mcp`'s origin: moving MCP to its own hostname would break passkey sign-in there (passkeys are bound to the site's host) and the session cookie, so `authorization_servers` would have to name the site's origin instead. Conformance runs: Claude Code, MCP Inspector, Codex and claude.ai's published client each sign in by CIMD and reach `/mcp`; Claude Code and claude.ai's client refresh, and after Disconnect none of them gets back in without consenting again. Turnstile on sign-up (sending an email code and starting Google or GitHub sign-in, the two ways an account gets made). A new passkey can approve at once only if it's the account's first, the account is under an hour old and its address is verified (sign-up; an OAuth account can arrive with someone else's unverified address), or the session adding it proved a passkey that can approve in the last 10 minutes (the sign-up passkey counts, so the second one the page asks for doesn't wait). Otherwise it waits 72 hours, and the notice to the verified address goes out before the passkey gets its date; if the address isn't verified or the send fails, the passkey is removed. A session cookie alone never vouches, so a stolen one can't skip the wait. A waiting passkey can sign in but can't vouch for another. Removing a passkey that approves needs the same 10-minute proof, so someone holding only the email can't delete the real passkeys and wait the owner out; a passkey that can't approve yet is removed without proof, each removal a single conditional delete. Removing your own last approving passkey is allowed after a warning: as with losing it, the next one goes through recovery (after the sign-up hour). Better Auth's rate limit is switched on explicitly (it keys off `NODE_ENV`, which Workers don't set), and the email-code password reset is off since nobody has a password. Session checks use a 5-minute cookie cache, so a short Neon outage signs nobody out. Every stage except prod also has dev sign-in (`apps/worker/src/dev.ts`): whoever holds `DEV_SIGN_IN_TOKEN` from Doppler `dev` becomes the fictional fixture student, or a tagged copy of it, without a code or passkey, and can mint a `/mcp` token for it. It never reaches prod three ways: `alchemy.run.ts` doesn't bind the token there, the Worker answers 404 for `/dev/` when `STAGE` is `prod`, and the deploy doctor reads the prod Worker's bindings and fails if the token is one. The token travels in the link's fragment and then a header, never a request URL, so request logs don't keep it (the browser's own history may); a wrong token looks the same as no route, and the comparison is over hashes in constant time. A dev session can add a passkey like any session, and on a fresh tagged account the first one approves at once; that reaches only fictional fixture accounts on non-prod stages. Managed fallbacks: Neon Managed Better Auth, then WorkOS AuthKit (see "Decisions").
- **Residency, stated narrowly**: EU accounts get EU-jurisdiction DOs and EU R2, and a Neon project in an EU region. Your own Claude processes what its tools return, under your Anthropic account's terms. Workers AI and treg providers may process data outside the EU. The settings page lists every processor and its region; anything not verified isn't claimed.
- **Backups, stated honestly**: DO point-in-time recovery (30 days) and R2 durability protect against bugs and mistakes, not against a Cloudflare-wide outage. A local copy, and the always-available export, are the real off-provider copies. Recovery targets: a single record restored within 4 hours, losing at most 1 hour of changes. A quarterly drill restores a fixture record (notes, files, schema, secret keys) into a staging stack and runs the parity tests on it.
