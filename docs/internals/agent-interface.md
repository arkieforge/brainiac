# Agent interface

MCP is the main way in. The same tools are served by `<domain>/mcp` (OAuth, works as a claude.ai connector on a normal subscription) and `brainiac mcp serve` (stdio for Claude Code, T3 Code, Codex). The tools' text, schemas and logic live in one module, `packages/base/src/tools.ts`. `brainiac mcp serve` forwards every message to `/mcp` with the device's token, so online its tools, answers and grants are the record's own by construction. When the record can't be reached it serves the same MCP server itself, answering `describe`, `query`, `get` and `search` from the local copy as the record last sent it (real revs), as the connection the daemon last synced with and only for that token, each answer marked `offline: true` with `syncedAt`. Proposals and revision history stay in the record, so offline `describe` counts no proposals (`null`) and asking for them refuses; offline `search` is keyword-only (`mode: "keyword"`), over that copy chunked as the record chunks it, not over `index.db`, which holds edits the record hasn't taken. Every write refuses and nothing is queued, and `related`, `ask` and `photos` refuse. The CLI has the same commands with `--json`. Brainiac supplies data and checks; the model doing the thinking is always yours.

## The filter

```
{ "type": "Project",
  "where": { "categories": { "has": "mobile" }, "synced.stars": { "gte": 50 }, "period.end": { "gte": "2025-01-01" } },
  "text": "flutter",
  "sort": ["-synced.stars"], "fields": ["title", "role", "links.repo", "synced.stars"], "limit": 10, "cursor": null }
```

- **Operators (start small)**: `eq in gte lte exists has text`. More only when a real query needs them.
- **Semantics**: a missing field matches only `exists: false`, and so do a null and an empty list; comparing with `null` is refused with that hint rather than read as no condition. `eq` on a list means "contains"; `has` is "contains" for a list and "has this key" for a mapping; dotted paths reach into mappings and lists (`sources.page`). Dates compare in UTC, a date-time against a plain date by its UTC day; strings compare case-insensitively after Unicode normalization, and `text` also ignores accents. Several operators in one condition must all hold. Rows pass the projection before the filter sees them.
- **Paging and cost**: stable cursors (sort key, then id; default sort `-date`, missing values last), bound to the query they came from; at most 100 rows a page (default 20); a query without a `type` over more than 10k notes is refused and asks for one. `type: "Proposal"` and `type: "Question"` list proposals (with `yours`) and the person's questions through the same filter (questions found from the schema and asked by agents, soonest deadline first, each naming the note and field its answer goes to; see "Questions"), and `type: "Check"` what the detectors flag (`packages/core/src/review.ts`), computed over only the notes the connection can see, so a check's evidence never comes from a note it couldn't read. An `Application` row also carries `checks`, computed and never stored: each requirement passing (with the notes that meet it), failing (with why, from stored values), or unsure for a connection that can't see every note, since a note it can't see may meet it. A drift check (one of the person's profiles says something else than the record) also carries `paste`, the record's text for the person to paste there. Agents read drift but never start a check: a check is paid, so only the person's Check now on the site does, besides the first read of a new profile.
- CLI shorthand: `brainiac query 'type:Project categories:mobile synced.stars>=50 sort:-synced.stars'`.

## Levels

| Level       | Can                                                                                                                 | Typical for                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| **read**    | describe, query, get, search, related, ask, draft, within the token's scopes                                        | A helper bot                 |
| **propose** | read + add, request_info, inbox leases, withdrawing its own proposals, and every change as a proposal               | Agents you don't fully trust |
| **write**   | propose + direct create, update, undo, organize plans, fill_form (subject to the hold window and the approval list) | Your own Claude              |

A background run (`brainiac mcp serve --background`, which the daemon's headless filer uses) gets at most propose and never the sensitive scope, whatever its connection was granted, and can't `add`, `import` or `withdraw` (see "Filer access" in [Security](security.md)).

When a call hits the approval list, the result is `needsApproval` with an `approval_id` and a `link` to `<domain>/approvals/<approval_id>` (a later MCP elicitation prompt would only show the link). Nothing changed: the record keeps the plan, and the page loads it from the record by its id, never from the URL, so the person signs exactly what the change will do. The agent gives the person the link, and once they have approved with their passkey, sends the same call again with `approval_id`; the record applies it only if its effect still hashes to the signed plan, once. Sending it again before they approve gets the same plan and id back. The same page lists every plan waiting, an agent's, a laptop's blocked sync edit or another tab's, and the person can turn one down, after which the agent's retry gets a new one. An agent, a token or an MCP tool can never approve: the routes take only the site's session and one of the person's passkeys. A dry run keeps no plan and gives no link.

## A session

```
You (in your Claude, whose connection you granted the sensitive scope): "My new IELTS result is in this PDF. Update everything that depends on it."
add       { file: "IELTS-TRF-2026.pdf", kind: "test-report" }    → unclassified until checks pass + your tap
          (you tap "test report" on your phone; server checks found no ID numbers → cleared, text p1)
query     { type: "TestScore", where: { test: "ielts-academic" } } → ielts-2025-03 (7.5, valid to 2027-03)
create    { type: "TestScore", from_document: …, supersedes: "ielts-2025-03.md", dry_run: true }
          → ielts-2026-11 (8.0; writing 7.0), sources per field
create    { …, dry_run: false }                → held { autoApplyAt: 2026-11-17, approveLink }
          (you approve early on your phone with your passkey; the note is created, unverified)
related   { id: ielts-2026-11 }                                   → TUM, KTH, Edinburgh checks re-ran
query     { type: "Application", where: { "checks.failing": { "exists": true } } }
          → Edinburgh: writing must be 7.5 or higher, the new attempt has 7.0 → failing
draft     { kind: "cv", for: "tum-msc-informatics-2027", from: "cv-v2" } → facts + template; Claude writes cv-v3
draft     { verify: cv-v3 }                                       → all values match
Claude: "Your November IELTS (8.0) is in as a new attempt; the 2025 one stays in history. TUM and KTH
still pass. Edinburgh needs 7.5 in writing and you have 7.0, so I've flagged it. The TUM CV is v3.
The score is labeled unverified until you mark it checked in review."
```

## Teaching the agent

- **Skill** (Claude Code plugin, also at `<domain>/skill.md`): call `describe` first; `query` before `search`; update rather than create; new events are new notes; quote values exactly as returned; run `verify` before giving numbers; dry-run bulk changes; never write vault files directly.
- **Hook**: the plugin installs a Claude Code hook that blocks Edit, Write and shell commands touching the vault path, plus Read, Grep and Glob on sensitive folders, `documents/files/`, `unorganized/` and `inbox/`, and points to the tools.
- **Prompts**: "file my inbox", "what's missing for <application>", "review my record", so a subscription user starts common jobs in one line.
- **Tested**: contract tests hold each tool to its schema and the connection's level through `/mcp`. Online, stdio returns the same tools and answers as remote. The `mcp-tool-use` eval runs real tasks on the models people use (see "Quality bar").
