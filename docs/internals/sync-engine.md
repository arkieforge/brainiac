# Sync engine

Every tab, phone, laptop daemon and agent talks to the person's Base DO over one small protocol. The browser and the CLI share one client (`packages/sync`).

## State on each client

| Layer              | What it is                                                                                                                                                                                                                       | Where                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **remote**         | The last server-acknowledged version of each note (rev and text). Sensitive notes only on a device you marked as yours with "keep sensitive notes" on; elsewhere they stay in memory and a restart fetches a snapshot            | IndexedDB / `.brainiac/state.db`                                                            |
| **pending**        | Your changes not yet acknowledged, in order, each with `clientSeq`, its base revision and the base text (so a three-way merge still works after server history has expired)                                                      | Same, durable across restarts                                                               |
| **server-waiting** | A remote change not yet written to disk, on filesystems without an atomic swap; shown in `describe` and on the site until you accept it                                                                                          | `state.db`                                                                                  |
| **blocked**        | Saved local edits the DO won't accept yet (conflict, needs approval, invalid), with the reason                                                                                                                                   | The file keeps your edit, marked "not synced: <reason>" in the CLI, the site and `describe` |
| **working**        | What you see: the UI state or the files on disk = remote + pending. Pending edits made on an older version show over the newest one, merged as the record will merge them, with your side kept where both changed the same thing | Screen / disk                                                                               |

Every change to these layers is written to the store as soon as it is made, and the send is never held
back for it: a send that outruns a write lost in a crash leaves the record's counters ahead of the stored
ones, so the next `welcome` makes the client repair. In a browser each open tab is its own client with its
own IndexedDB slot, held with a Web Lock; a closed tab's slot, pending edits and all, goes to the next tab
that opens.

## Protocol

```
// client → DO (one WebSocket per client; packages/core protocol.ts, checked on arrival)
hello    { clientId, cursor: seq | null, lastAssigned: clientSeq, ackedUpTo, schemaVersion, appVersion, attempt }
mutate   { clientId, clientSeq, changeId, ackedUpTo, noteId, baseRev, change, approvalId? }   // changeId: random per change
         change: create { path, raw, class } | put { raw, base } | delete { base }   // base: the text it was made on
// DO → client
welcome  { clientId, highWater, ackedUpTo }   // answer to hello
snapshot { seq, notes, attempt }       // answers hello `attempt`: cursor missing, ahead of the record, or older than the 90-day log
changes  { from, to, items }            // each note changed after `from`, as it is at `to`: catch-up, then live
result   { clientId, clientSeq, changeId, ok, rev?, conflict?, needsApproval?: { planHash, items }, error? }
gap      { clientId, highWater }        // resend from highWater + 1
reset    { clientId, clientSeq, reason } // two machines share this id
```

The DO computes each mutation's digest itself. A result names the `changeId` it answers, so a copy that
shares a `clientId` never takes another machine's result as its own: a mismatch makes it repair. A client
takes only the snapshot answering its latest hello; an older one has been overtaken. That one is taken even
when its seq is below the cursor, since the record may have been restored. A `needsApproval` result carries
the plan the person signs (each note's base revision, path, class and effect) and its hash. Once they approve on
the site, the client resends the edit with the `approvalId` under a new `clientSeq` and a new `changeId`: the
record answers a `changeId` it has seen with the answer it gave.

- **Each socket reads as its principal**: the route that opens it sets who it speaks for, from the session or
  token: the person, or a connection. What a connection may read comes from its own row in the record, read
  again for every message and push. Changing a connection's grants closes its open sockets, so its client says
  hello again and gets a snapshot that names every note it may no longer hold as withheld; a disconnected one
  can't reconnect. `snapshot`, `changes` and every push pass through the read projection
  (`project` in `packages/base`), so a socket without the sensitive scope never gets a sensitive note. A
  note it may not see, or one that just turned sensitive, comes as deleted and `withheld`, in snapshots too:
  the device drops it the way it drops a note that turned sensitive, file, index and history, even while
  paused, and learns its id and when it changes, nothing else. A hello under another principal than the client's cursor was
  earned under gets a snapshot. Its changes to such a note are refused as if there were no note. Paths are one
  namespace across classes, as on disk, so creating a note at a path a hidden note holds fails: a caller can
  confirm a path it guessed exactly, but a refusal never names another note's path.

- **Exactly once, in order**: each client's mutations are applied strictly in sequence. The DO accepts only `highWater + 1`; a gap is refused, so the client resends in order. Results are kept until the client acknowledges them. A duplicate older than that gets "already processed, reconcile": the client re-reads that note's current revision, which is enough because the change log or a snapshot shows what happened.
- **Every result consumes its number**: a mutation that comes back as a conflict, `needsApproval` or invalid still uses up its `clientSeq` (the high-water mark advances in the same transaction); the edit moves to _blocked_, and the queue keeps going. Resending it later (after you approve or fix it) takes a new number. Acknowledgment is implicit: every `hello` and `mutate` carries `ackedUpTo`, and the DO drops results and digests up to that point. A reconcile never discards local intent: if the client's edit differs from what the server has, it goes back in the queue with its **original** base revision and base text, so it passes through the three-way merge and can't silently overwrite another device's later change.
- **Two machines, one identity** (for example a full OS migration while the old laptop still runs): a `clientSeq` that arrives with a different digest, or one the DO has already dropped, gets a `reset` naming it. The copy that still holds that change as pending repairs under a new id; the other ignores it, so a late duplicate never resets a healthy client.
- **Repair** resends every pending change in order, exactly as it was made (same `changeId`, same base text), under the new id. The record keeps every answer it gave, by `changeId`, for 90 days, so a change it has seen before gets the same answer again without being applied again: a note deleted or reverted since stays that way, and no proposal is opened twice. Anything else goes through the merge rules below.
- **Copies and restores are caught**: the OS config folder holds a device id for the machine, and `state.db` records which device owns its pending queue. A copied vault on another machine sees a different owner, discards the copied queue and repairs: it diffs files against the server, with no base for any of them, so a difference becomes a conflict rather than an overwrite and nothing replays twice. A machine restored from an old backup learns it from `welcome`: the DO's high-water mark is above the last `clientSeq` it assigned, or the DO has seen it acknowledge more than it has. It takes a new `clientId` and repairs the same way. The client decides, because a late `hello` carries old counters and only the client knows its current ones. No edit is dropped, and none is applied twice.
- **Held proposals** live only in the DO and are never applied to working copies until released (see "The contract").
- **Version skew**: `hello` carries schema and app versions. An outdated CLI can still read but must upgrade before writing changes it doesn't understand, and it is told exactly that.
- **Ordering** comes only from the DO's `seq`. Device clocks are display-only.

## Merge rules (nothing is dropped silently)

| Both sides changed…                                 | Result                                                                                                                    |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Different fields                                    | Merged automatically                                                                                                      |
| The same field, to different values                 | **Conflict**: both values kept in a conflict proposal; the note keeps the server value, marked "conflict", until you pick |
| The same field, to the same value                   | Merged                                                                                                                    |
| The body, in separate places                        | Three-way text merge                                                                                                      |
| The body, in the same place                         | Conflict, both versions kept                                                                                              |
| One edited, one deleted                             | Conflict: the note is restored with the edit and flagged                                                                  |
| A held proposal vs a newer change to the same field | On release, the proposal becomes a normal conflict instead of applying                                                    |

**One rule for local edits the server won't take**: a saved local edit that hits a conflict, needs an approval (for example a verified field edited in Obsidian) or fails validation stays in your file, marked "not synced" with the reason. Remote changes to that one note wait until you resolve it (approve, pick a side, or fix the YAML); everything else keeps syncing. A refused edit clears when an edit made on its text lands (you fixed it). A conflict clears once the record moves past the revision it was kept at: someone picked a side, or changed the note again. The protocol has no signal yet for a proposal being decided, so in the second case your conflicting value then lives on only in the proposal and the displaced versions, not in the file.

## Guards on the local copy

- **Mass changes pause**: if more than 50 notes or 10% of the record would change from disk at once (a bad git checkout, a script gone wrong), the daemon stops and asks. It counts notes, not files (a move is one), and the 10% only from 5 notes, so a few saves together in a small record never pause it. `brainiac resume` syncs them, `brainiac resume --undo` writes the record's versions back (what they replace is kept for `brainiac restore`). A vault folder deleted outright also pauses: nothing is deleted in the record, and `brainiac repair` writes the folder back, pending changes included.
- **Paths are input too**: from the record, from `state.db` (it sits in the vault) and from disk, the daemon reads and writes only plain files at note paths inside the vault: never through a symlink, never into a hidden folder. Sensitive notes it doesn't keep leave the device whole: file, index entry and displaced versions.
- **What the daemon keeps outside the vault**: its lock, pid and request files live in the user's config folder, so deleting the vault can't take them and nobody who can only write the vault can plant them. One daemon per vault, by an OS lock. A file a sync write displaced is kept aside in `.brainiac/displaced` for 10 minutes and read again after each batch, so an editor still writing into its open copy is caught; kept files and temp files carry their note's id or name, so a crash mid-write is recovered on the next start. An editor holding a file open longer than that is missed.
- **Other sync tools**: iCloud, Dropbox, Google Drive and Obsidian Sync folders are detected and warned about by `brainiac doctor`. Their conflict copies are ignored, except Google Drive's ("name (1).md" is also a name people choose), which sync as notes of their own.
- **Broken YAML** in a hand-edited note: the note is held back with the line number shown; everything else keeps syncing.
- **Two local files, two promises**: `.brainiac/index.db` (search) is derived, and `brainiac repair` rebuilds it from files plus the server. `.brainiac/state.db` (pending changes with base text, blocked edits) is authoritative and written with SQLite's write-ahead log. If it is ever lost, your files are still intact: repair diffs each file against the server and turns the differences into pending changes or conflicts, so nothing is overwritten, though some merges may need you.
- **Bundled SQLite**: the CLI ships its own SQLite with FTS5, rather than relying on the OS copy.
