# Sync engine

Every tab, phone, laptop daemon and agent talks to the person's Base DO over one small protocol. The browser and the CLI share one client (`packages/sync`).

## State on each client

| Layer              | What it is                                                                                                                                                                  | Where                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **remote**         | The last server-acknowledged version of each note (rev + raw hash)                                                                                                          | IndexedDB / `.brainiac/state.db`                                                            |
| **pending**        | Your changes not yet acknowledged, in order, each with `clientSeq`, its base revision and the base text (so a three-way merge still works after server history has expired) | Same, durable across restarts                                                               |
| **server-waiting** | A remote change not yet written to disk, on filesystems without an atomic swap; shown in `describe` and on the site until you accept it                                     | `state.db`                                                                                  |
| **blocked**        | Saved local edits the DO won't accept yet (conflict, needs approval, invalid), with the reason                                                                              | The file keeps your edit, marked "not synced: <reason>" in the CLI, the site and `describe` |
| **working**        | What you see: the UI state or the files on disk = remote + pending                                                                                                          | Screen / disk                                                                               |

## Protocol

```
// client → DO (one WebSocket per client; packages/core protocol.ts, checked on arrival)
hello    { clientId, cursor: seq | null, lastAssigned: clientSeq, ackedUpTo, schemaVersion, appVersion, attempt }
mutate   { clientId, clientSeq, changeId, ackedUpTo, noteId, baseRev, change }   // changeId: random per change
         change: create { path, raw, class } | put { raw, base } | delete { base }   // base: the text it was made on
// DO → client
welcome  { clientId, highWater, ackedUpTo }   // answer to hello
snapshot { seq, notes, attempt }       // answers hello `attempt`: cursor missing, ahead of the record, or older than the 90-day log
changes  { from, to, items }            // each note changed after `from`, as it is at `to`: catch-up, then live
result   { clientId, clientSeq, changeId, ok, rev?, conflict?, needsApproval?, error? }
gap      { clientId, highWater }        // resend from highWater + 1
reset    { clientId, clientSeq, reason } // two machines share this id
```

The DO computes each mutation's digest itself. A result names the `changeId` it answers, so a copy that
shares a `clientId` never takes another machine's result as its own: a mismatch makes it repair. A client
takes only the snapshot answering its latest hello; an older one has been overtaken. That one is taken even
when its seq is below the cursor, since the record may have been restored. `needsApproval` and an
`approvalId` on `mutate` arrive with approvals (#12).

- **Exactly once, in order**: each client's mutations are applied strictly in sequence. The DO accepts only `highWater + 1`; a gap is refused, so the client resends in order. Results are kept until the client acknowledges them. A duplicate older than that gets "already processed, reconcile": the client re-reads that note's current revision, which is enough because the change log or a snapshot shows what happened.
- **Every result consumes its number**: a mutation that comes back as a conflict, `needsApproval` or invalid still uses up its `clientSeq` (the high-water mark advances in the same transaction); the edit moves to _blocked_, and the queue keeps going. Resending it later (after you approve or fix it) takes a new number. Acknowledgment is implicit: every `hello` and `mutate` carries `ackedUpTo`, and the DO drops results and digests up to that point. A reconcile never discards local intent: if the client's edit differs from what the server has, it goes back in the queue with its **original** base revision and base text, so it passes through the three-way merge and can't silently overwrite another device's later change.
- **Two machines, one identity** (for example a full OS migration while the old laptop still runs): a `clientSeq` that arrives with a different digest, or one the DO has already dropped, gets a `reset` naming it. The copy that still holds that change as pending repairs under a new id; the other ignores it, so a late duplicate never resets a healthy client.
- **Repair** resends every pending change in order, exactly as it was made (same `changeId`, same base text), under the new id. The record keeps every answer it gave, by `changeId`, for 90 days, so a change it has seen before gets the same answer again without being applied again: a note deleted or reverted since stays that way, and no proposal is opened twice. Anything else goes through the merge rules below.
- **Copies and restores are caught**: the `clientId` lives in the OS config folder, and `state.db` records which `clientId` owns its pending queue. A copied vault on another machine sees a different owner, discards the copied queue and runs `brainiac repair`, which diffs files against the server, so nothing replays twice. A machine restored from an old backup learns it from `welcome`: the DO's high-water mark is above the last `clientSeq` it assigned, or the DO has seen it acknowledge more than it has. It takes a new `clientId` and repairs the same way. The client decides, because a late `hello` carries old counters and only the client knows its current ones. No edit is dropped, and none is applied twice.
- **Held proposals** live only in the DO and are never applied to working copies until released (see "The contract").
- **Version skew**: `hello` carries schema and app versions. An outdated CLI can still read but must upgrade before writing changes it doesn't understand, and it is told exactly that.
- **Ordering** comes only from the DO's `seq`. Device clocks are display-only.

## Merge rules (nothing is dropped silently)

| Both sides changed…                                 | Result                                                                                                                    |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Different fields                                    | Merged automatically                                                                                                      |
| The same field, to different values                 | **Conflict**: both values kept in a conflict proposal; the note keeps the server value, marked "conflict", until you pick |
| The same field, to the same value                   | Merged                                                                                                                    |
| The body, in separate places                        | Three-way text merge                                                                                                      |
| The body, in the same place                         | Conflict, both versions kept                                                                                              |
| One edited, one deleted                             | Conflict: the note is restored with the edit and flagged                                                                  |
| A held proposal vs a newer change to the same field | On release, the proposal becomes a normal conflict instead of applying                                                    |

**One rule for local edits the server won't take**: a saved local edit that hits a conflict, needs an approval (for example a verified field edited in Obsidian) or fails validation stays in your file, marked "not synced" with the reason. Remote changes to that one note wait until you resolve it (approve, pick a side, or fix the YAML); everything else keeps syncing.

| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| Other tabs, phone                         | Live push                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | < 300 ms             |
| Laptop, daemon running                    | Live push; file written atomically (temp + rename); index updated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | < 1 s                |
| Laptop asleep or daemon off               | Catch-up from the cursor on wake or start. `brainiac daemon install` registers a login service (launchd, systemd, Windows)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Seconds after waking |
| CLI or local MCP read                     | The daemon already knows if it's behind; without a daemon, one cursor check before the read. Offline answers say "local copy, synced 3 h ago"                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Before the answer    |
| A file you changed and saved locally      | A save the daemon has seen is never overwritten: it's sent as a pending change and merged, or kept as "not synced" with the reason. The daemon replaces a file with an atomic swap that keeps whatever it displaced (Linux `renameat2` with `RENAME_EXCHANGE`, macOS `renamex_np` with `RENAME_SWAP`, Windows `ReplaceFileW` with a backup file, called through `bun:ffi`). If the displaced file isn't the version it expected, including a save that landed a moment earlier, that file becomes your pending change and the server's version a conflict. Displaced versions are also kept in `state.db` for 7 days (`brainiac restore <file>`). On filesystems without a swap call, the daemon never replaces files: remote changes to a note you have on disk wait as a pending server version (shown in `brainiac review` and on the site) until you accept them, and `brainiac doctor` explains why | On save              |
| Unsaved text in an editor                 | Brainiac can't see it. Obsidian reloads changed files; other editors may warn. Brainiac promises only that saved files are never overwritten                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | n/a                  |
| Drafts and packets that used an old value | Marked stale with the change shown; submitted versions stay frozen                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Immediately          |

## Guards on the local copy

- **Mass changes pause**: if more than 50 notes or 10% of the record would change from disk at once (a deleted vault, a bad git checkout), the daemon stops and asks.
- **Other sync tools**: iCloud, Dropbox and Obsidian Sync folders and their conflict copies are detected, warned about at setup, and ignored.
- **Broken YAML** in a hand-edited note: the note is held back with the line number shown; everything else keeps syncing.
- **Two local files, two promises**: `.brainiac/index.db` (search) is derived, and `brainiac repair` rebuilds it from files plus the server. `.brainiac/state.db` (pending changes with base text, blocked edits) is authoritative and written with SQLite's write-ahead log. If it is ever lost, your files are still intact: repair diffs each file against the server and turns the differences into pending changes or conflicts, so nothing is overwritten, though some merges may need you.
- **Bundled SQLite**: the CLI ships its own SQLite with FTS5, rather than relying on the OS copy.
