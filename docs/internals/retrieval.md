# Retrieval

One pipeline in the cloud (SQLite in the DO) and on a laptop (SQLite through Bun), from one package. Deterministic lookups are exact by construction. Answers are written by your own model, and any answer can be checked against the record with one call.

## Authorization comes first: one projection for every read

A single function, `project(note, principal)`, decides which fields, body and files a caller may see. `query`, `search`, `get`, `related`, `describe`, history, MCP resources, file URLs, `ask` context and every cache use it. The index is built so it can't leak:

- **Chunks never mix privacy classes**: normal fields and body go in one chunk family; sensitive fields in another, in a separate FTS table and vector set. A note marked sensitive puts its body in the sensitive family. Searches run only over the families the caller may see, before ranking.
- **Field scopes** on tokens (for example "Education and Roles only") filter the note list before search.
- **Secrets and vault documents are never indexed**, and local-only material never enters the cloud index.
- **Restrictions apply at once**: deleting a note, making it sensitive or local-only, or narrowing a token deletes or moves the affected chunks and vectors in the same transaction, before any re-index job runs. Every search hit is also re-checked against the note's current class and the caller's current scopes before ranking. A short gap in search results during the re-index is accepted; a leak isn't.
- **Tested with canaries**: fixture values planted in sensitive fields must never appear in any tool output, snippet, embedding neighbor or cache entry for a principal without access.

## Ingest

`mutation commits` → `job in outbox` → `extract` → `normalize` → `chunk by class` → `embed` → `install if rev matches`

- **Extract**: a `file` job runs `toMarkdown` on a PDF's text layer (plain text, markdown and CSV are read as they are), and the vault's checks run over all of it before anything is indexed, so what search holds is exactly what the checks read. A page that fails a confidence check (garbled text, a table with no numbers) needs reading; since the checks can't vouch for it, its file stays unclassified, and so does a PDF that can show more than its text layer (an image, an attached file, form fields). Photos and a PDF's JPEGs (a scan) go through OCR (the `apps/ocr` Worker: Tesseract, after Cloudflare Images decodes and scales the picture), but only so the checks find what they print and a passport's MRZ is parsed: OCR can't vouch it saw everything an image says (a tilted, faint or blurred corner beside text it reads leaves no trace), so a photo or a scan never clears, and its text never reaches search or an agent. Getting a photo read and filed is the person's own Claude's job: once the person lets it see one, the `photos` tool hands it over as an image, and a scan as its pages' images. Every value keeps its page.
- **Normalize**: front-matter is flattened into readable text ("IELTS Academic overall 8.0, writing 7.0, expires 2028-11-02") so fields are searchable as text too.
- **Chunk**: a short note is one chunk; a long one (a body over 2,000 characters), one chunk per H2; a cleared file, one per page. A template header names the note and type ("[TestScore · IELTS Academic, Nov 2026]"), or a file's kind and page ("[transcript · page 2]"), with no model call. A note's chunks take its class's family; a cleared file's, its own class's.
- **Embed**: multilingual bge-m3 (Workers AI), stored as int8 with the model name. Changing models, chunking or extraction (`INDEX_VERSION`) re-indexes the record in the background on its next wake while the old chunks carry search; a record from before vectors gets them the same way.
- **Local copies** hold chunks but no vectors. Online, `brainiac mcp serve` forwards every call to the DO, which embeds the question, so what a device holds never changes an answer (sensitive notes it doesn't hold, the default, included); the parity test compares remote and stdio at the floor and with the sensitive scope. Offline, `describe`, `query`, `get` and `search` answer from the local copy, and an answer to a connection with the sensitive scope on a device that doesn't keep sensitive notes says they are cloud-only there (`cloudOnly`). Sensitive chunks never sync to a device that hasn't opted in. Offline, and for local-only notes, search is keyword-only, and results say so (`mode: "keyword"`); a parity test holds a laptop's offline answers (index.db, and stdio `search`) to the record's, for a laptop that keeps sensitive notes (the person's answers) and one that doesn't (a reader without the scope).
- **Languages**: FTS5's `unicode61` cut Bangla and Hindi words at every vowel sign and virama, so a fragment like `কম` matched inside `কম্পিউটার`. Its `categories 'L* N* Co M*'` keeps combining marks inside words. Text and questions are also folded before FTS5 sees them (NFC, then Arabic harakat, tatweel and zero-width joiners removed), so a vocalized Arabic word matches the plain one, and Bangla র‍্য or a Persian word with a ZWNJ isn't cut at the joiner. A trigram index wasn't needed, and wouldn't have helped Arabic, where the marks sit between letters. Tested on both engines.

## Retrieve and answer

| Route      | When                                   | How                                                                                          | Model call |
| ---------- | -------------------------------------- | -------------------------------------------------------------------------------------------- | ---------- |
| **field**  | "my IELTS writing score"               | `query` on fields                                                                            | none       |
| **list**   | "all my published papers"              | Filter + sort                                                                                | none       |
| **graph**  | "what's missing for TUM"               | Requirement checks + edges                                                                   | none       |
| **search** | "my work on transit apps"              | FTS5 + exact vector top-k, merged by reciprocal rank fusion, plus one hop of graph neighbors | none       |
| **open**   | "which of my projects fit an NLP PhD?" | search, then whole notes to the model                                                        | yours      |

- **Search** ranks each visible family by BM25 and every visible vector by exact int8 cosine (all of them, read and scored in the DO's memory: 70 ms p95 at 20k chunks in workerd, keyword-only 12 ms, not counting the question's embedding), one row per note or file page, and fuses the best 100 of each ranking by reciprocal rank (`1 / (60 + rank)`) before the limit (at most 100) cuts. Each hit says whether it `matched` the words, the meaning or both: one found by meaning alone holds none of the question's words. Visibility is checked in SQL before any ranking, then by `project`. A chunk from an older revision only nominates its note: the snippet is cut from the note's current text, and words that text no longer holds don't count as matching it. Then one hop: notes a hit's relations or body links name, and notes whose relations or body links name a hit (any relative `.md` path or note id in the front-matter, and `[text](path.md)` in the body, resolved as approvals resolve `supersedes`), read from the notes at query time, so they are never stale, and each projected.
- **A question isn't a search**: `ask` context matches notes holding _any_ of the question's words (BM25 still ranks the rare ones highest), while `search` needs every word. "What was my writing score" shares one or two words with the note that answers it, and offline there are no vectors to make up the rest.
- **Routing is plain rules**: field names and glossary terms in the question, list words, application names. No model is needed to route.
- **Context**: whole notes rather than fragments, capped at about 60k characters (some 15k tokens), with `me.md` first (`describe` has the schema). Loading a whole small record instead of retrieving is an option the evals must prove, not a default.
- **Citations name the exact field**: `<note id>#sections.writing@2`, or `file:<sha256>#p1` for a page of a cleared file. Answers use the current revision. Values from fields nobody verified are labeled _unverified_.
- **What `verify` guarantees, exactly**: the agent sends its text plus a list of claims, each `{note, field, value}`. Every claim must equal that field at the **current** revision, so "writing 8.5" claimed against `sections.writing` fails when the field holds 7.0. As a cheap safety net, numbers and dates in the text not covered by a claim come back as "uncited": a claim covers one mention of its number, so two sections both 7.0 take two claims. A claim covers its number wherever the text says it: that the text says it of the right field is the model's to get right. Everything else in the prose ("I was accepted", "a strong background in NLP") is not verified, and Brainiac doesn't claim it is. The checks confirm claims match the record; they don't certify the record.

## Who writes the answer

| Where                                                     | Model                                                                                                                                                                | How exactness is kept                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **In your Claude** (MCP: Claude Code, claude.ai, T3 Code) | Yours, on your subscription                                                                                                                                          | `ask` returns the context, the canonical field values and the citation list, not prose. The skill tells the agent to quote values as given and cite them. `ask {mode: "verify", text, claims}` checks a draft's explicit claims against current field values, flags uncited numbers and dates, and returns mismatches to fix |
| **On the site**                                           | The command palette answers field, list and graph questions itself (no model). Open questions get "Open in Claude", which hands them off with the connector attached | Deterministic routes are exact by construction                                                                                                                                                                                                                                                                               |

Rerankers are added only if the retrieval eval shows a real gain.

Measured by the `retrieval` and `answers` evals (see "Quality bar"): recall@8, citation precision, exact-field accuracy (must be 100% of shown values), and refusal correctness, local and cloud.
