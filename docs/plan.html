Brainiac: your whole record, ready for every application Uni, study abroad, scholarships, jobs. One record, live everywhere, run by you and your own Claude.

People sign up, and everything an application asks for lives in one place: achievements, projects, papers, grades, test scores, CVs, recommendation letters, IDs, profiles and links, as typed markdown notes with sources. It syncs live to the site, the phone and any laptop that keeps a local copy. People work on it with the Claude they already pay for (Claude Code, claude.ai, T3 Code) through MCP or a thin CLI. No API key is needed, and the record works fully with or without anything on disk. Secrets sit in a vault that agents can use only in approved ways and never see, the way treg keeps keys server-side. Risky changes need your approval, and values nobody has checked are labeled as unverified.

Name

What makes it different

Typed facts with proof

Memory products store loose snippets. Brainiac stores typed notes whose front-matter is validated data, with sources tied to the exact fields they prove. "Is my CGPA 3.84 or 3.87?" has one answer and a page to show for it.

Your Claude does the work

Filing, organizing, drafting and answering run in the Claude you already use, on your subscription. Brainiac supplies the record, the tools and the checks. Risky changes need an approval only you can give, tied to that exact change.

Exact, and honest about it

Numbers and dates come straight from stored fields, every answer can be checked against the record, and values nobody has verified are labeled as unverified. Profiles out in the world (LinkedIn, GitHub, Scholar) are checked for drift.

The contract: the rules every other section follows

One set of rules for authority, models, permissions, approvals, privacy and retention. When any other section seems to say something different, this section wins.

1. Who holds the truth

  • The person's Base Durable Object (DO) is the authority for every synced note. A laptop folder is a working copy: editable offline and synced through the protocol in "Sync engine".
  • Local-only notes (an explicit opt-in per note or folder): the disk is the authority. They never reach the cloud; the site shows only a count. There is no hold window and no approval list on disk: anything with your shell can change a local-only note.
  • The stored form is the raw markdown text. Front-matter is parsed from it for queries. An edit changes only the YAML node or the markdown block it touches: every byte outside it stays as it was. A property test checks exactly that.

2. Models: your subscription, not ours

  • Every model task (filing the inbox, reading a hard scan, answering, drafting, organizing) runs in the person's own agent on their own subscription: Claude Code, claude.ai (web, desktop, phone) with the Brainiac connector, T3 Code, Codex, or any MCP client.
  • Brainiac itself runs no Claude and needs no API key. It runs only cheap, deterministic infrastructure: document-to-text (Workers AI toMarkdown), embeddings, search, checks.
  • Later, for people who add their own API key: an Ask box and a hosted filer on the site itself.
  • Brainiac never stores or proxies anyone's subscription login.

4. What always needs your approval

Everyone enrolls a passkey at sign-up (sign-in is Better Auth, self-hosted, with a second passkey requested at sign-up). Approving is a WebAuthn passkey assertion whose challenge is the plan hash (the list of note, base revision and patch it covers), checked in the DO with SimpleWebAuthn. The signature itself ties you to that exact change. A review session signs one session nonce instead, valid for 10 minutes and renewed only by a new signature. It covers just verify, fix and undo on the items shown in that session; scope grants, privacy loosening, secret use and bulk deletes always need their own plan-hash signature. An agent, a token, a settings note or a confirm box inside a chat client can never create an approval; they only show the approval link.

  • Any change whose effect alters, clears or deletes a value you verified, or sets verification, however it arrives: an update, a delete, an undo, a move or type change, a replacement or a schema change. The DO checks the transaction's result against its own verification records, so clearing verified first and then editing doesn't get around this.
  • Deleting more than 5 notes, or an update matching more than 20
  • Loosening privacy (for example making a sensitive note normal, or a local-only note synced)
  • Granting or raising a connection's level or a token's scope
  • Using a secret whose policy is ask, submitting a form, and emailing anyone but you
  • organize runs that move or convert notes, schema merges and new top-level areas

Losing your passkeys: two passkeys are requested at sign-up. If both are lost, recovery is sign-in plus a 72-hour wait, with a notice to every verified email address, before a new passkey can approve anything.

Agents get a redacted summary instead. Passport fields come from a deterministic MRZ parse on the server: name, nationality and dates go to the note, and the number goes to the vault. Any note or folder can additionally be made local-only, when a local copy exists. That trades cloud features for that note for never leaving the disk.

What a laptop copy holds: by default, normal notes, their files and your local-only notes. Sensitive notes stay in the cloud unless you choose "keep sensitive notes on this laptop" for a device you marked as yours. Vault-document files are never written to disk; only their sidecar note is. On disk, the sensitive scope binds only Brainiac's tools, not other programs that read files, and the plan says so. Brainiac's Claude Code hook also blocks Read, Grep and Glob on sensitive folders, documents/files/ and inbox/.

6. Retention and deletion

  • Deleted notes are tombstones for 30 days, then purged. Undo works from revision history (inverse changes) for 30 days.
  • Deleting an account removes live data (DO storage, R2 files, indexes, Neon rows) within 24 hours. Disaster-recovery copies (DO point-in-time recovery, Neon's restore window) expire within 30 days and are never restored into a deleted account.
  • Processors and what they keep (email delivery logs, treg call logs) are listed on the settings page.

Architecture: Cloudflare + Neon, built with Alchemy

Each person's record lives in its own Durable Object with its own SQLite database: the record, its change feed, its search index and its live connections. Neon holds what is shared across users (accounts, billing, the base registry). R2 holds files. One Worker serves every hostname. All of it is declared in one alchemy.run.ts.

Why one Durable Object per person

  • Isolation by construction: each record is a separate database. A query bug can't return another person's rows, because they aren't in the database being queried.
  • Parity by construction: the DO and the CLI both run SQLite with FTS5 through one package (packages/base), so cloud and local run the same queries.
  • Ordering: every mutation is one SQL transaction that assigns the next seq. Because a DO only interleaves requests while one is awaiting I/O, a mutation never awaits anything external between reading the revision and committing.
  • Live and cheap: hibernating WebSockets cost nothing while idle.
  • Fits the size: a record is about 5 to 50 MB of SQLite; the cap per DO is 10 GB, and files go to R2.

Background work that survives crashes

  • Transactional outbox: any mutation that needs follow-up work (extract, embed, reindex, render) writes a jobs row in the same transaction. A DO alarm dispatches pending jobs to the Queue and keeps retrying until they're acknowledged. After a restart, pending jobs are dispatched again.
  • Inbox filing is a job too: the item waits in the DO until an agent (your Claude) claims it with a lease, so two agents never file the same item.
  • Revision-checked results: a job carries the note revision it was made for. Its result is installed only if the note is still at that revision; otherwise it's dropped and a job for the new revision runs.
  • No retrieval holes, no stale text: until new chunks replace them, old chunks are used only to find candidate notes; what's returned (snippets, context) always comes from the note's current revision. A stale snippet is never shown.

Alternatives considered

  • Convex: built-in live sync, but every query must filter by base, and its engine differs from local SQLite. It's the fallback if the DO sync layer ever costs more than it saves.
  • Neon Realtime (beta since 2026-10-15): live SQL queries over WebSockets. Revisit when it is GA and documents resuming an offline client from a cursor. Not used now.

How files are organized

  • No file stands alone: every PDF, scan or photo has a sidecar note (Document or Photo) saying what it is, who issued it, when it expires and which fields it proves.
  • Relations are relative paths in front-matter (readable, Obsidian-friendly, valid OKF). Every note also has a ULID id for sync. When a note moves (by you, an agent or organize), the DO rewrites every reference to it, in front-matter and in body links, in the same transaction, and every copy receives the rewritten notes.
  • Names: kebab-case <what>-<when>. Portal file names (Karim_Nadia_Transcript.pdf) are applied only when building a packet.
  • Distinct events are distinct notes: two IELTS attempts are two TestScore notes, the newer one supersedes the older. "Current score" is a query, and history stays queryable.
  • Source and generated output are separate: out/ and derived/ can be rebuilt; versions you actually submitted are frozen on the application.
  • Filenames are normalized to Unicode NFC and checked case-insensitively for clashes, so macOS, Windows and Linux copies agree.

The knowledge graph

Notes are nodes. Edges come from relation fields declared in the manifest (proves, for, supersedes, referee) plus body links, and a meets edge exists only while a requirement check passes. Edges are stored with inverses and rebuilt in the same transaction as the note.

  • "What's still missing for TUM?" → requirements whose check fails: the APS certificate and a second letter.
  • "Which applications break if my IELTS expires?" → checks with valid_on after the expiry date.
  • "What proves my CGPA?" → the source with fields: [cgpa], its document and page.

Sync engine: live, conflict-safe, offline-safe

Every tab, phone, laptop daemon and agent talks to the person's Base DO over one small protocol. The browser and the CLI share one client (packages/sync).

Protocol

// client → DO
hello    { clientId, cursor: seq | null, lastAssigned: clientSeq, ackedUpTo, schemaVersion, appVersion }
mutate   { clientId, clientSeq, ackedUpTo, noteId, baseRev, digest, patch, approvalId? }
// DO → client
snapshot { seq, notes }                 // cursor missing or older than the 90-day log; client rebases pending on it
changes  { from, to, items }            // catch-up, then live
result   { clientId, clientSeq, ok, rev?, conflict?, needsApproval?, error? }
  • Exactly once, in order: each client's mutations are applied strictly in sequence. The DO accepts only highWater + 1; a gap is refused, so the client resends in order. Results are kept until the client acknowledges them. A duplicate older than that gets "already processed, reconcile": the client re-reads that note's current revision, which is enough because the change log or a snapshot shows what happened.
  • Every result consumes its number: a mutation that comes back as a conflict, needsApproval or invalid still uses up its clientSeq (the high-water mark advances in the same transaction); the edit moves to blocked, and the queue keeps going. Resending it later (after you approve or fix it) takes a new number. Acknowledgment is implicit: every hello and mutate carries ackedUpTo, and the DO drops results and digests up to that point. A reconcile never discards local intent: if the client's edit differs from what the server has, it goes back in the queue with its original base revision and base text, so it passes through the three-way merge and can't silently overwrite another device's later change.
  • Two machines, one identity (for example a full OS migration while the old laptop still runs): a clientSeq that arrives with a different digest, or one the DO has no digest for while the client still holds it as pending, resets that client and runs repair.
  • Copies and restores are caught: the clientId lives in the OS config folder, and state.db records which clientId owns its pending queue. A copied vault on another machine sees a different owner, discards the copied queue and runs brainiac repair, which diffs files against the server, so nothing replays twice. A machine restored from an old backup sends a hello whose last assigned clientSeq is below the server's high-water mark: it is treated as a reset, gets a new clientId, and repairs the same way. No edit is dropped, and none is applied twice.
  • Held proposals live only in the DO and are never applied to working copies until released (see "The contract").
  • Version skew: hello carries schema and app versions. An outdated CLI can still read but must upgrade before writing changes it doesn't understand, and it is told exactly that.
  • Ordering comes only from the DO's seq. Device clocks are display-only.

Guards on the local copy

  • Mass changes pause: if more than 50 notes or 10% of the record would change from disk at once (a deleted vault, a bad git checkout), the daemon stops and asks.
  • Other sync tools: iCloud, Dropbox and Obsidian Sync folders and their conflict copies are detected, warned about at setup, and ignored.
  • Broken YAML in a hand-edited note: the note is held back with the line number shown; everything else keeps syncing.
  • Two local files, two promises: .brainiac/index.db (search) is derived, and brainiac repair rebuilds it from files plus the server. .brainiac/state.db (pending changes with base text, blocked edits) is authoritative and written with SQLite's write-ahead log. If it is ever lost, your files are still intact: repair diffs each file against the server and turns the differences into pending changes or conflicts, so nothing is overwritten, though some merges may need you.
  • Bundled SQLite: the CLI ships its own SQLite with FTS5, rather than relying on the OS copy.

RAG: retrieval that is exact where it matters

One pipeline in the cloud (SQLite in the DO) and on a laptop (SQLite through Bun), from one package. Deterministic lookups are exact by construction. Answers are written by your own model, and any answer can be checked against the record with one call.

Authorization comes first: one projection for every read

A single function, project(note, principal), decides which fields, body and files a caller may see. query, search, get, related, describe, history, MCP resources, file URLs, ask context and every cache use it. The index is built so it can't leak:

  • Chunks never mix privacy classes: normal fields and body go in one chunk family; sensitive fields in another, in a separate FTS table and vector set. A note marked sensitive puts its body in the sensitive family. Searches run only over the families the caller may see, before ranking.
  • Field scopes on tokens (for example "Education and Roles only") filter the note list before search.
  • Secrets and vault documents are never indexed, and local-only material never enters the cloud index.
  • Restrictions apply at once: deleting a note, making it sensitive or local-only, or narrowing a token deletes or moves the affected chunks and vectors in the same transaction, before any re-index job runs. Every search hit is also re-checked against the note's current class and the caller's current scopes before ranking. A short gap in search results during the re-index is accepted; a leak isn't.
  • Tested with canaries: fixture values planted in sensitive fields must never appear in any tool output, snippet, embedding neighbor or cache entry for a principal without access.

Typed tables like applications or links are not stored separately: they're queries over notes.fm (with generated columns and indexes for hot fields). Dedupe is per record, never global, so no one can probe whether someone else uploaded a file.

Security and privacy

  • Isolation: one DO per record; the base id comes from the session or the token (tokens embed it), never from a URL; R2 keys are built server-side; CI runs a cross-tenant attack suite against every route and tool.
  • Authorization projection on every read surface, including indexes, caches and file URLs (see "RAG"), with canary tests.
  • Approvals are WebAuthn passkey signatures over the plan hash, verified in the DO (see "The contract"). Two passkeys are requested at sign-up; losing both means a 72-hour recovery wait with notices.
  • Prompt injection: the main risk is your own Claude reading a hostile PDF or email and then acting. Inside Brainiac, everything that can destroy or leak through Brainiac (secret use, form submits, email, privacy loosening, permission changes, bulk deletes, verified values) is on the approval list, which no agent can satisfy. Text from files, emails and pages is also marked untrusted in tool results, as a hint.
  • What Brainiac can't stop: anything a connection can read, your Claude can send elsewhere through its other connectors (email, web). So the sensitive scope is off by default for every connection; you grant it per connection when you connect your own Claude, and the default is checked by a canary eval.
  • Filer access: automatic background filing (no person present) handles normal material only. Sensitive items wait for your own Claude session whose connection you granted the sensitive scope; that connection keeps exactly the access you granted, and the inbox lease only makes it the one agent filing that item. Unclassified items stay redacted for everyone until your confirmation tap clears them. The daemon's headless connection is propose-level. It starts headless runs in an empty working directory with --restricted --tools "" (no built-in tools, user and project settings ignored), --strict-mcp-config with a config containing only Brainiac, and --allowedTools "mcp__brainiac__*", so the run can't reach a shell, files or your other connectors. A filing eval case starts a real headless run and asserts its actual tool inventory is Brainiac's tools and nothing else. Changes to numbers, dates or verified facts come as proposals with the source page.
  • Laptop copies: on disk, the sensitive scope binds only Brainiac's tools, not programs that read files. That's why sensitive notes stay in the cloud by default, vault-document files are never written to disk, and the hook blocks Read, Grep and Glob on sensitive folders, documents/files/ and inbox/. The daemon uploads inbox files right away and keeps them out of the local index.
  • Email-in: accepted only from your verified addresses; anything else is quarantined for you to release. Attachments go through the same ingest checks as uploads.
  • Uploads: type sniffed from bytes, size caps per plan, decompression limits, executables rejected, Office macros flagged, HTML and SVG served only from the sandboxed origin.
  • Auth: Better Auth 1.7, self-hosted in the Worker with its tables in Neon: passkeys (sign-in and approvals share the same credentials), email codes, Google and GitHub, JWT, and @better-auth/mcp + @better-auth/cimd as the OAuth 2.1 server for MCP (2026-07-28 profile). $0 at any scale, but we own OAuth security. One team reported CIMD's fetcher doesn't run on Workers, so M0 tests that first; the fallback is client registration with a consent page plus an allowlist of known clients (claude.ai, Claude Code, T3 Code, Codex). M0 also runs OAuth conformance tests: MCP Inspector, the claude.ai connector, Claude Code, token audience, refresh rotation. Turnstile on sign-up. Managed fallbacks: Neon Managed Better Auth, then WorkOS AuthKit (see "Decisions").
  • Residency, stated narrowly: EU accounts get EU-jurisdiction DOs and EU R2, and a Neon project in an EU region. Your own Claude processes what its tools return, under your Anthropic account's terms. Workers AI and treg providers may process data outside the EU. The settings page lists every processor and its region; anything not verified isn't claimed.
  • Backups, stated honestly: DO point-in-time recovery (30 days) and R2 durability protect against bugs and mistakes, not against a Cloudflare-wide outage. A local copy, and the always-available export, are the real off-provider copies. Recovery targets: a single record restored within 4 hours, losing at most 1 hour of changes. A quarterly drill restores a fixture record (notes, files, schema, secret keys) into a staging stack and runs the parity tests on it.

Quality bar: cheap infrastructure, fast, correct, proven

"Works 100 out of 100" means two things. The deterministic parts (sync, schema, filters, permissions, approvals, merges, secrets, requirement checks, the verify step) must be correct every time, and tests check it from many angles, including property tests over thousands of random cases. The model parts run in the user's own Claude, so Brainiac's job is to make the right answer easy and a wrong number catchable, and evals measure how well that works on the models people actually use.

Tests (deterministic, every PR, free)

  • Unit: packages/core (schema, merges, filter compiler, chunker, YAML patching), packages/base (SQL and migrations on both bun:sqlite and the DO).
  • Property tests (fast-check): random edits across 3 simulated clients with disconnects and offline periods always converge with nothing lost; random filters return the same rows locally and in the DO; a YAML or body edit leaves every byte outside the edited node unchanged; and the approval invariant: random sequences of update, delete, undo, move, type change, schema change and superseding create from actors without an approval never change a verified value or the verified set, and never escape the hold.
  • DO integration in the Workers test pool: protocol, high-water marks, client reset, jobs outbox, migrations, scopes, approvals, hibernation.
  • End to end on an Alchemy preview stage per PR (its own Neon branch): sign-up with a passkey, import, edit, approve, a web edit reaching a laptop file, an offline conflict, a blocked local edit.
  • Real filesystem: the daemon's file adapter runs against real editors' save patterns (atomic rename, in-place write) with concurrent saves interleaved at every step of the swap, on macOS and Linux in M0 and Windows in M1.
  • Chaos: kill a DO mid-write, drop and reorder messages, a laptop offline for 100 days, a cloned vault, a machine restored from a week-old backup, a deleted vault.
  • Security: cross-tenant suite on every route and tool, canary non-disclosure across every read surface (including that a new connection gets no sensitive data until you grant the scope), forged and replayed approval signatures, vault documents never reaching an agent, injection corpus, XSS uploads, secret-leak scan of all test logs and outputs.
  • Parity: the fixture record and questions, local (online) vs cloud: identical results.
